# 교수자 운영 안내

이 문서는 공개 운영 절차만 담습니다. 명단·학번 매핑·성적·평가 메모는 LMS나 교수자 관리 공간에서 다룹니다.

## 저장소 역할과 권한

- 9~10주차는 학생이 만든 공개 개인 저장소를 사용합니다. 직접 생성·연결하는 경험을 템플릿 배포로 대신하지 않습니다.
- 11주차는 이 저장소의 fork에서 원본으로 PR을 보냅니다. 학생에게 원본 쓰기 권한을 일괄 부여하지 않습니다.
- 공통 main은 교수자/관리자가 CI와 학생 리뷰를 확인한 뒤 merge commit으로 병합합니다. 학생의 댓글 리뷰와 보호 규칙의 필수 승인을 구분합니다.
- 보호 규칙은 PR 경유와 `tests` 검사 통과를 요구하되, 현재 소유자 혼자 관리하는 공통 저장소에 별도 승인자 1명을 강제하지 않습니다. 실제 검토는 병합 전 수행합니다. 조교를 추가할 때 승인 역할을 재설계합니다.
- 12~14주차에는 템플릿의 기본 branch로 공개 팀 저장소를 만들고 팀원에게 쓰기 권한을 줍니다. 팀 저장소에서는 동료 승인 1명과 테스트 통과를 요구하도록 설정할 수 있습니다.
- 공통 저장소를 Organization으로 옮길 필요는 없습니다. Organization·팀 저장소 생성과 실제 학생 초대는 수강 계정 목록에 맞춰 별도로 진행합니다.

## 수업 전

1. Ubuntu에서 Python 3.10+, Git, venv와 GitHub 인증을 확인합니다.
2. README의 설치·실행·테스트 명령으로 시작 코드가 동작하는지 확인합니다.
3. 학생용 경로로 fork → PR을 시험해 원본 대상과 CI 실행 승인 대기를 확인합니다.
4. T01 반복 Issue는 계속 열어 두고 파일별 별칭이 겹치지 않게 합니다. 코드 Issue는 한 명/한 팀씩 배정합니다.
5. 현재 19명은 3인 팀 5개와 4인 팀 1개로 편성할 수 있습니다. 최대 40명은 4인 팀 10개가 한 가지 구성입니다.

## PR 검토

학생끼리 먼저 목적·실행 결과·차이를 검토하게 한 뒤 교수자가 확인합니다. 반복 CSV 과제의 PR은 공통 Issue를 `Refs`로 연결하고, 작업 한 건을 끝내는 코드 PR만 `Closes`로 연결합니다.

fork PR의 워크플로가 실행 승인을 기다리면 diff와 특히 workflow 변경을 먼저 확인합니다. 승인 대기는 학생의 코드 실패가 아닙니다. 수업 종료 시 교수자 병합 대기 때문에 제출을 미완료로 처리하지 않습니다.

Actions는 공개 저장소의 표준 Ubuntu runner에서 짧게 실행합니다. 학생 PR에는 읽기 전용 권한만 사용하고 관리 토큰·개인 비밀정보를 제공하지 않습니다. CI 통과는 자동 점수가 아니며 학생이 바꾼 테스트와 workflow도 함께 검토합니다.

## 제출과 평가

- LMS에 PR URL, 타인 리뷰 URL, 검증한 commit SHA, 실제 실행 결과를 받습니다.
- 마감 뒤 변경 가능한 branch 이름 대신 제출 SHA를 기록합니다.
- 코드 작성·리뷰·실행 확인 역할을 순환하고 개인 설명을 확인합니다.
- 데이터 첫 기여는 진입 활동입니다. 각 학생은 이후 팀 단계에서 Python 코드와 테스트에도 참여합니다.
- GitHub 자체에는 자동채점 결과나 성적을 공개하지 않습니다. Actions에는 테스트 성공/실패와 오류 정보만 남깁니다.

## 과제 확장

T02~T07을 한 학급에서 모두 소진할 필요는 없습니다. 팀 템플릿의 시작 코드와 완료 기준으로 재사용할 수 있습니다. 학생 기능이 공통 저장소에 병합되면 다음 팀의 시작 버전을 정하고 배포할 commit을 기록합니다.

팀 생성·권한 배포와 전체 PR 현황 취합 스크립트는 이 저장소의 현재 필수 구성에 포함하지 않습니다. 우선 6개 팀의 링크를 LMS에서 관리하고, 필요하면 교수자용 별도 도구로 확장합니다.
